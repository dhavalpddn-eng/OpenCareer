## Career start
**F-22/KRME is a developer validation fixture only.** A standard new career starts from scratch: no owned F-22, no automatic military access and no required aircraft ownership. The player builds from entry training/employer/rental/assigned-aircraft work appropriate to qualifications, then earns access, financing and ownership through progression.

## Flight rules
Normal jobs cold-and-dark at parking; mission profiles may authorize runway starts. Block/pushback time != pilot flight time. Commercial multi-leg turns require park/shutdown/service. Rejected takeoff is distinct; no takeoff count. Crash preserves partial record; insurance may allow **1 redo/day, no carryover**. Disconnect only suspends; no short timeout; resume on plausible continuity. Sim-rate allowed anytime, but career credit = `wall_delta * min(rate,1)`. Legit safety decisions may earn small bounded credit; no farming. Landing scoring aircraft-relative when trusted data exists. Use simulator time/weather; normal night fixed-wing jobs need suitable lighting. Actual-instrument credit needs simulated IMC evidence. Initial progression is simplified FAA-style; aircraft experience is layered: total -> category/class -> propulsion/complexity -> family -> model/type -> recency/TO/L.

## Aircraft registry / runway feasibility
Slice 1 adds provider-neutral aircraft/runway records, Application source boundaries and deterministic `Feasible / Infeasible / InsufficientData` runway compatibility with explicit reasons. Slice 2 adds deterministic multi-provider aircraft resolution: exact canonical identity grouping only, field-level confidence precedence/provenance, installed-vs-known status, and explicit unresolved capability fields. Slice 3 uses the official MSFS 2024 `SimConnect_EnumerateSimObjectsAndLiveries` API to enumerate spawnable user-selectable aircraft on the existing serialized SimConnect worker. Livery variants collapse to one installed-aircraft identity and discovery becomes unavailable again on disconnect. Slice 4 adds local `aircraft.cfg` enrichment behind Infrastructure using exact `[FLTSIM.N] title` matching. It reads documented ICAO metadata, `icao_engine_count` / `icao_engine_type`, `ui_max_range`, and passenger `capacity` when the file is locally present. `capacity` is kept as passenger-capacity reference metadata because the SDK defines it as excluding pilot/copilot; it does not silently populate OpenCareer's existing `Seats`. Missing/invalid/streamed CFG data stays unknown, and ambiguous duplicate local definitions fail closed. Slice 5 adds provider-neutral airport/runway observations with explicit provenance and authority plus a cached resolver. `LocalSimulator` observations always outrank reference sources and are queried fresh; reference results may be cached. Airport facts are never merged across authority levels, so an MSFS-local runway with unknown length/width/surface stays unknown rather than being silently filled from an external source. Slice 6 implements that MSFS 2024 facility path with documented `SimConnect_AddToFacilityDefinition`, `SimConnect_RequestFacilityData`, `SIMCONNECT_RECV_FACILITY_DATA`, and `..._END` messages on the existing serialized worker. It maps airport name/ICAO and child runway length, width, surface, end identifiers, and closed-end flags into the Slice 5 `LocalSimulator` observation contract. Requests are serialized one at a time, bounded by timeout/cancellation, and request-specific SimConnect exceptions are correlated by send ID so a failed airport lookup degrades to no local observation without dropping healthy telemetry. Hosted tests validate ABI decoding and worker behavior; the native facility call still needs a focused real-MSFS lookup check, not another full FlightSession flight. Slice 7 adds deterministic operation-level physical screening against only the aircraft fields needed for that decision: known maximum payload, known maximum range, runway performance, and origin/destination runway data. It preserves explicit unknowns, reports payload/range over-limit values, and no longer requires unrelated fields such as seats or IFR capability before those physical checks can run. Slice 8 adds an optional provider-neutral dispatch-performance profile with field provenance/confidence for operating empty weight, MTOW, maximum fuel weight, and an authoritative payload-range envelope. When planned fuel is supplied, missing dispatch-performance or weight/fuel fields fail closed; known fuel-capacity and loaded-takeoff-weight violations are explicit. Payload-range points are validated and linearly interpolated only inside their documented coverage; no extrapolation is invented. Range and runway-length safety margins are explicit caller inputs rather than hidden constants. Slice 9 adds provider-neutral dispatch weather observations and an optional weather source boundary. Weather is normalized into runway-relative sustained/gust headwind/crosswind components plus optional density altitude before Domain evaluation, avoiding hidden magnetic-vs-true heading assumptions. Explicit crosswind, tailwind and optional density-altitude limits participate in runway candidate selection, so a shorter compatible runway may be chosen when the longest runway fails wind limits. Missing weather remains `InsufficientData`, while known runway/weight failures remain authoritative. Slice 10 adds the first MSFS-local weather adapter without using deprecated SimConnect weather-station APIs. The existing serialized worker optionally samples `PLANE LATITUDE`, `PLANE LONGITUDE`, `AMBIENT WIND DIRECTION`, `AMBIENT WIND VELOCITY`, and `DENSITY ALTITUDE` once per second; optional weather setup failure does not take down normal telemetry. The facility definition now also carries airport/runway coordinates and runway true heading. Because MSFS ambient wind SimVars are user-aircraft-position values, the adapter returns simulator weather only when the fresh aircraft sample is within the requested airport/runway geometry; remote airports fail closed rather than reusing local wind. Runway-relative components use the documented true heading, respect closed runway ends, and do not fabricate gusts. Slice 11 wires the established planning chain into the production WinUI service graph: SimConnect installed-aircraft observations plus read-only local `aircraft.cfg` enrichment feed `AircraftRegistryCatalogService`; the local SimConnect airport observation feeds `CachedAirportDataSource`; the Slice 10 local-weather source feeds `OperationDispatchPlanningService`. `MsfsUserConfigLocator` discovers existing Steam/Store `UserCfg.opt` locations and an optional `OPENCAREER_MSFS2024_USERCFG` override, then reads only `InstalledPackagesPath`; missing paths simply yield no CFG enrichment. The LiveProbe now supports `--airport <ICAO>` and the PowerShell wrapper exposes `-Airport`; after live telemetry begins it records facility provenance/runways plus local weather/wind evidence and returns nonzero when the focused validation cannot establish both. Slice 12 extends that exact-title local aircraft source to read sibling `flight_model.cfg` and `flight_performance.cfg` only when they are unambiguous and locally present. It maps documented `max_takeoff_weight`, `max_landing_weight`, `max_zero_fuel_weight`, `max_gross_weight` fallback semantics and `empty_weight` into explicit configured-weight facts. MSFS `empty_weight` is intentionally not mislabeled as OpenCareer operating-empty weight. A documented `AIRCRAFT_LOADING fuel_capacity` is converted to maximum fuel weight only when `ENGINE_PERFORMANCE fuel_density_table` contains exactly one valid density; multi-fuel density tables remain unknown and zero-fuel capacity is preserved as known zero. Contradictory weight facts fail closed. Slice 13 adds provider-neutral conditioned performance grids for the documented modern CFG nD table format. Direct takeoff/landing ground-roll and 50-foot total-distance tables preserve aircraft weight (lb), OAT (°C), pressure altitude (ft) and distance (ft). Indexed cruise profiles preserve profile identity/fuel type plus TAS and fuel-consumption grids by weight, ISA deviation and pressure altitude. Axes must be finite, rectangular and strictly increasing; table outputs must be finite/non-negative. The model uses bounded trilinear interpolation only inside the supplied envelope and returns unknown outside it—no extrapolation. Malformed individual tables fail closed without destroying independent valid tables, and non-consecutive cruise sections are not reinterpreted. Slice 14 wires the direct 50-foot total-distance tables into operation runway screening through explicit `DispatchRunwayPerformanceConditions` for predicted takeoff/landing weight, OAT and pressure altitude. When a total-distance table exists it outranks the static baseline length for that endpoint; missing conditions or a lookup outside the published grid returns `InsufficientData` and cannot fall back to the static minimum. The existing runway-length safety margin is applied after bounded interpolation. Takeoff and landing conditions are independent. Ground-roll-only tables are deliberately not treated as equivalent to the 50-foot total-distance requirement. Pressure altitude remains a caller input and is not replaced by Slice 9/10 density altitude. A zero/invalid resolved distance also fails closed rather than throwing or producing a zero runway requirement. Definite runway/surface/weather failures still outrank an unrelated conditioned-performance unknown. No V-table/aerodynamic fallback is invented. Hosted CI proves deterministic dispatch integration; native MSFS facility/weather behavior still needs the focused live lookup. Visibility/ceiling, remote destination weather, cruise planning, pilot ratings, career qualifications and government/military authorization remain separate later gates. No Jobs generator exists yet. Slice 15 adds a dedicated `CruisePerformancePlanner` plus `CruisePerformancePlanningService`, registered in the production service graph. Planning requires an explicit cruise profile index, fuel-type index, predicted cruise weight, ISA deviation and pressure altitude. The selected profile must match the requested fuel type exactly; the planner never auto-selects another profile or substitutes fuel. TAS and fuel-consumption grids are resolved independently at the same condition through Slice 13 bounded interpolation; a missing grid or any lookup outside its published envelope returns `InsufficientData`, zero TAS fails closed, and a published zero fuel-consumption value remains valid source data. The resulting plan preserves profile identity/name, fuel type, TargetMach metadata, TAS and gallons/hour. It does not yet convert cruise performance into route time, trip fuel, reserves, climb/descent burn or range authority. Hosted validation for code head `b28c64e` passes Linux 29/29 SimLab + 411/411 xUnit and Windows WinUI/LiveProbe + 411/411 xUnit; reported builds have 0 warnings/errors. Slice 16 adds `RouteFuelEstimator` plus `RouteFuelPlanningService`, registered in production composition. Route inputs explicitly separate total route distance from cruise-segment distance and require caller-supplied climb/descent time and fuel; Slice 15 TAS/GPH are applied only to the cruise segment. Trip fuel is explicit climb + cruise + descent fuel. Contingency is an explicit percentage of trip fuel; final reserve is explicitly modeled as minutes at the selected cruise-consumption rate, with a separate additional-reserve-gallons input. There are no hidden reserve defaults. Slice 15 failure reasons propagate through the route planner with no fallback. The result remains gallons-only: taxi/ground burn, alternate routing, climb/descent performance derivation, regulatory reserve authority, fuel-density conversion, fuel-capacity/weight authority and range authority remain separate. Hosted validation for code head `4708c9c` passes Linux 29/29 SimLab + 438/438 xUnit and Windows WinUI/LiveProbe + 438/438 xUnit; reported builds have 0 warnings/errors.
