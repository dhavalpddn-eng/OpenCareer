## Confirmed gameplay

- First live test hub: **KRME Griffiss International**; mixed civilian/government/defense/UAS context. Do not invent a resident fighter wing or real-world missions that are not documented.
- **F-22/KRME is only the first developer live-telemetry validation fixture. It is not the required career start.** A standard new career starts from scratch with no owned aircraft and no automatic military access. Early progression may use training, employer, rental or assigned aircraft appropriate to qualifications; ownership and military access are earned separately.
- First owned used light aircraft should become reasonably attainable around **50–80 real flying hours** through actual savings/financing, not an hour unlock.
- Typical sessions 1–3 hours; support up to ~6 and recover interrupted sessions where technically possible.
- Home airport, local route connections, relationships, hangar/storage and additional bases matter; no teleporting the company around the map.
- Bankruptcy is possible but should usually require sustained bad decisions; employee work remains a recovery path.
- Management is mostly automatic. Eligible manual ground procedures may provide modest bounded rewards.
- Military-heavy airports produce much more military/government work while retaining appropriate civilian work.
- Military/rented/employer/assigned aircraft are distinct from owned aircraft.
- **Levels may be added later as meaningful meta-progression.** They may summarize experience or unlock convenience/prestige, but never bypass licenses/ratings, reputation, military authorization, aircraft capability, affordability or dispatch rules.
- Flight-session rules are now specified in `docs/flight-session-design.md`: tracking begins after aircraft load/stable telemetry, real-world-style movement time is distinct from load time, one session may contain multiple legs, bounce recontacts are one landing episode, touch-and-go is recorded distinctly from full-stop, safe diversions/go-arounds are not automatic failures, and conventional jobs default to destination parking + shutdown unless the mission defines another terminal condition.
- Free/practice flights can be logged for pilot experience. Career-credit hours are distinct from accelerated simulated time so time acceleration remains usable without multiplying license/aircraft-experience progression. Material teleport/slew displacement and aircraft changes cannot advance normal career jobs.
- Cargo requirements are now specified in `docs/cargo-market-requirements.md`: generated cargo work carries named commodity lots (coffee, phones, televisions, food, plants and an extensible catalog) with quantity, physical properties, declared/market value and origin/destination economics rather than anonymous cargo weight.
- Onboarding is layered: a general app tutorial, a first-job tutorial, and versioned first-time mission-family tutorials for specialized procedures. Unique missions such as banner pickup and carrier takeoff/landing receive their own live guided checklists with Controller/Keyboard bindings and telemetry-driven completion only where the state can be verified. See `docs/intro-tutorial.md` and `docs/mission-tutorial-system.md`.
- 2026-09-17 cross-plugin flight review is recorded in `docs/flight-system-research-2026-09-17.md`. It strengthens Chapter 4 with pilot-log dimensions (day/night/cross-country/instrument/event attributes), planned-vs-actual route/diversion evidence, evidence provenance/confidence and bounded adaptive landing telemetry. External cloud/AI services remain optional and non-authoritative.

## Connection and telemetry boundary implemented

- `src/OpenCareer.Application/Simulator`: `ISimulatorConnection`, `ISimulatorTelemetrySource` and immutable status/identity boundary types. The application layer references normalized Domain telemetry, not SimConnect SDK types.
- `src/OpenCareer.SimConnect`: documented native calls through P/Invoke, all owned by one dedicated worker. Open acknowledgement, data-definition setup, user-aircraft subscription, pause event subscription, dispatch, liveness requests and close remain serialized off the UI thread.
- Correlated `RequestSystemState("Sim")` checks liveness every five seconds, with a 30-second response timeout. Menus are valid responses. Empty dispatch is not proof of a disconnect.
- On `SIMCONNECT_RECV_OPEN`, the worker installs one 1 Hz numeric telemetry definition and subscribes to `Pause_EX1`. Setup failure prevents a false Connected state.
- First normalized snapshot uses the existing `Domain/Telemetry/AircraftTelemetrySnapshot`: position, MSL/AGL altitude, IAS/ground speed, vertical speed, true heading, pitch/bank/G, on-ground, parking brake, engine count/running state, fuel, derived payload, flaps, gear, pause and slew.
- SDK-specific normalization is contained in `OpenCareer.SimConnect`: feet/second vertical speed becomes feet/minute, headings are normalized, SimConnect booleans treat any nonzero value as true, flaps are converted to 0–100%, and payload is conservatively derived as `max(0, total weight - empty weight - fuel weight)`.
- Telemetry is cleared when a connection/session ends so stale aircraft data cannot survive a disconnect.
- Tests inject native-call results/raw callback buffers; they verify mapping, packet validation, worker ownership, pause handling and stale-data clearing. Native DLL execution is **not** tested by these mocks.
- Runtime: supply the installed MSFS 2024 SDK's x64 `SimConnect.dll` through `MSFS2024_SDK` or `-p:SimConnectNativePath=...`. It is copied beside the app, never committed. A build without the DLL launches with connection unavailable; with the DLL and MSFS closed it should show Waiting for MSFS.
- Exact setup, SDK references, telemetry definitions and remaining Windows live checks: `docs/simulator-connection.md`.
- `tools/OpenCareer.LiveProbe` reuses the production `SimConnectConnection` and writes connection/telemetry JSONL traces; `tools/run-live-probe.ps1` resolves the SDK DLL and launches it. This is validation tooling only and does not implement flight state.
- `tools/OpenCareer.TraceAnalysis` reads those captures on Windows/Linux without the SDK. It reports connection/pause/clearing observations, field ranges, snapshot cadence and line-numbered integrity findings. Tests are synthetic; analysis changes no flight state, certifies no live behavior and calibrates no thresholds.

## Material limits

The first installed-aircraft discovery adapter is implemented using the official MSFS 2024 `SimConnect_EnumerateSimObjectsAndLiveries` API on the existing serialized SimConnect worker. It discovers spawnable user-selectable aircraft titles/liveries, collapses livery variants to one exact title-based canonical identity, marks those identities installed, and becomes unavailable on disconnect. It intentionally supplies no fabricated capability/performance values. Slice 4 adds a local `aircraft.cfg` Infrastructure source using exact SimConnect-title matching and the documented `InstalledPackagesPath` package-root model. Locally available CFG files may enrich ICAO identity metadata, engine type/count, UI max range and passenger capacity; missing/invalid/streamed files remain unknown and ambiguous duplicate definitions return no enrichment. Passenger `capacity` is not mapped to OpenCareer `Seats` because the SDK defines it as excluding pilot/copilot. Slice 5 adds provider-neutral airport/runway observations, provenance/authority, and a cached resolver behind `IAirportDataSource`. Local simulator observations have deterministic precedence over reference providers and are not cross-filled from lower-authority data; unknown runway length/width/surface therefore stays unknown and dispatch remains fail-closed. Slice 6 implements the official MSFS 2024 facility-data request/decoder adapter on the existing serialized SimConnect worker. A static AIRPORT -> RUNWAY definition requests `NAME64`, `ICAO`, runway length/width/surface, primary/secondary end number/designator and closed flags. One facility request is active at a time; cancellation, timeout, immediate HRESULT failure and correlated asynchronous SimConnect exceptions return no local observation without taking down healthy telemetry. Hosted tests cover raw message decoding, worker ownership, mapping, incomplete lists, disconnect cleanup and failure isolation. Native DLL execution of this facility path still needs a focused real-MSFS airport lookup check; the completed FlightSession live flight does not need to be repeated. Slice 7 adds operation-level physical screening using field-level aircraft resolution instead of requiring a fully populated aircraft profile: known payload capacity, known maximum range, runway performance and origin/destination runway compatibility can now be evaluated while unrelated fields remain unknown. Missing payload/range/runway facts remain `InsufficientData`; definite payload/range/runway failures remain `Infeasible`. Slice 8 adds a provider-neutral `AircraftDispatchPerformanceProfile` resolved with the same confidence/provenance rules. It may carry operating empty weight, MTOW, maximum fuel weight and validated payload-range points. Supplying planned fuel activates fail-closed weight/fuel checks; loaded takeoff weight and fuel-capacity violations are deterministic. Payload-range interpolation is allowed only between supplied authoritative points and never extrapolates beyond the highest documented payload. Explicit range and runway-length safety-margin percentages are applied before comparison. Slice 9 adds `AirportDispatchWeatherObservation`, runway-relative sustained/gust wind components, optional density altitude, explicit weather authority/provenance, and the `IAirportDispatchWeatherSource` Application boundary. Crosswind/tailwind and optional density-altitude limits are explicit operation inputs with no hidden defaults. Weather participates during runway candidate evaluation rather than after runway selection, allowing another physically compatible runway to be selected when wind blocks the longest runway. Missing weather or runway wind data remains `InsufficientData`; a definite physical failure still wins over an unrelated weather unknown. The Domain does not derive components from runway numbers, so no magnetic-vs-true heading approximation is invented. Slice 10 adds `SimConnectLocalAirportWeatherSource`. The existing SimConnect worker optionally samples user-aircraft latitude/longitude, ambient wind direction/velocity and density altitude once per second; optional weather setup failure leaves normal telemetry healthy. Facility data now also carries airport/runway coordinates and runway true heading. Because supported ambient wind SimVars describe the user-aircraft position, simulator weather is published only when a fresh sample is local to the requested airport/runway geometry. Remote airport lookups, stale samples, malformed values and disconnects return no simulator weather. Runway-relative wind uses facility true heading, considers only open runway ends, and leaves gusts unknown rather than fabricating them. Deprecated SimConnect weather-station APIs are not used. Slice 11 activates the planning chain in the WinUI production composition. `SimConnectInstalledAircraftObservationSource` and `MsfsAircraftCfgObservationSource` feed `AircraftRegistryCatalogService`; `SimConnectAirportDataObservationSource` feeds the authoritative-first `CachedAirportDataSource`; `SimConnectLocalAirportWeatherSource` feeds `OperationDispatchPlanningService`. `MsfsUserConfigLocator` checks existing standard Steam/Store `UserCfg.opt` roots plus optional `OPENCAREER_MSFS2024_USERCFG`, reads package locations without modifying simulator files, and returns no enrichment when configuration/packages are unavailable. No external airport provider is added or made authoritative. The focused LiveProbe path accepts `--airport <ICAO>` / PowerShell `-Airport`, records local facility provenance/runway facts and normalized local weather evidence after live telemetry begins, and returns a failure code when both cannot be established. Slice 12 extends the exact-title local configuration observation with conservative sibling-file dispatch enrichment. `flight_model.cfg [WEIGHT_AND_BALANCE]` may supply configured empty weight, MTOW, maximum landing weight and maximum zero-fuel weight; documented MSFS fallback semantics are honored only when the specific parameter is absent, while an explicitly invalid value remains unknown. Configured `empty_weight` is stored separately and is not treated as OpenCareer operating-empty weight. `flight_performance.cfg [AIRCRAFT_LOADING] fuel_capacity` is converted from gallons to maximum fuel pounds only when `[ENGINE_PERFORMANCE] fuel_density_table` has exactly one valid density. Multiple densities, missing files, invalid values and ambiguous sibling definitions stay unknown; a zero fuel capacity remains a known zero. Contradictory configured empty/MTOW data rejects the dispatch profile rather than leaking partial unsafe facts. Slice 13 adds `AircraftPerformanceGrid3D` and `AircraftConditionedPerformanceProfile` to preserve documented MSFS modern nD performance tables without flattening them. Direct takeoff/landing ground-roll and 50-foot total-distance tables retain weight/OAT/pressure-altitude axes; cruise profiles retain their index/name/fuel-type metadata and TAS/fuel-consumption grids with weight/ISA-deviation/pressure-altitude axes. The parser follows the documented rectangular table order with the final axis varying fastest, rejects malformed dimensions/non-monotonic axes/negative outputs, and preserves independent valid tables when another table is malformed. Grid lookup supports exact cells and bounded trilinear interpolation only within the supplied axes; requests outside the envelope return unavailable rather than extrapolating. Slice 14 adds `DispatchRunwayPerformanceConditions` to operation requirements and makes supplied 50-foot total-distance tables condition-aware runway authority. Origin takeoff and destination landing each use their own predicted weight, OAT and pressure-altitude inputs. If the relevant total-distance grid exists, its bounded interpolated result replaces the static baseline length for that endpoint before the existing explicit runway safety margin is applied. Missing inputs, outside-envelope lookups or a resolved zero/invalid distance fail closed as endpoint-specific `InsufficientData`; the static length is not used as a fallback when the higher-authority conditioned table exists. Ground-roll-only grids remain source facts and do not substitute for total-distance screening. Density altitude is not substituted for pressure altitude. When no total-distance table exists, established baseline runway screening is unchanged. Conditioned distance can fill a previously unknown baseline length while width/surface requirements remain independently enforced, and a definite runway/surface/weather incompatibility still determines `Infeasible` even when another conditioned input is unknown. No V-table/aerodynamic fallback is implemented. Hosted CI verifies the dispatch integration; native facility/weather validation remains a separate live step. Visibility/ceiling, remote destination weather, cruise planning, approach suitability, qualifications and authorization remain separate unimplemented gates. Market-driven Jobs generation is still not implemented. Slice 15 adds a dedicated `CruisePerformancePlanner` and Application `CruisePerformancePlanningService`, registered in the WinUI planning composition. A caller must explicitly provide cruise profile index, fuel-type index, planned cruise weight, ISA deviation and pressure altitude. The planner requires an exact profile/fuel-type match, never chooses another profile automatically, resolves TAS and fuel-consumption grids independently at the same condition with Slice 13 bounded interpolation, and returns `InsufficientData` for missing tables or any outside-envelope lookup. A zero TAS cell is unusable and fails closed; zero fuel consumption remains a valid published table value. Successful output preserves profile identity/name, fuel type, TargetMach metadata, TAS and gallons/hour only. Route time, trip fuel, reserves, climb/descent burn and range authority remain unimplemented. Hosted validation at code head `b28c64e` is green: Linux 29/29 SimLab + 411/411 xUnit; Windows WinUI and LiveProbe builds + 411/411 xUnit; reported builds show 0 warnings/errors. Slice 16 adds `RouteFuelEstimator` and `RouteFuelPlanningService`, registered in production composition. Inputs separate total route distance from cruise-segment distance and require explicit climb/descent time and fuel. Slice 15 TAS/GPH drive only cruise time and cruise fuel; they are not applied to total-route distance or non-cruise phase duration. Trip fuel is climb + cruise + descent fuel, contingency is an explicit percentage of trip fuel, and final reserve is explicitly minutes at cruise consumption plus optional additional reserve gallons. No reserve values are silently defaulted. Slice 15 lookup failures remain `InsufficientData` with the original cruise failure reason. Output remains gallons-only and is not yet fuel-capacity, takeoff-weight, regulatory-reserve or range authority because selected-fuel density is not preserved as a verified conversion boundary. Hosted validation at code head `4708c9c` is green: Linux 29/29 SimLab + 438/438 xUnit; Windows WinUI and LiveProbe builds + 438/438 xUnit; reported builds show 0 warnings/errors. Slice 17 preserves indexed MSFS `fuel_density_table` values as provider-neutral `AircraftFuelDensity` facts and uses the documented zero-based index relationship to `fuel_type_idx`. `RouteFuelWeightBridge` converts Slice 16 required gallons to pounds only from the exact selected density; missing data or index mismatch fails closed. `RouteFuelWeightPlanningService` exposes that conversion through Application, and production DI is registered.
